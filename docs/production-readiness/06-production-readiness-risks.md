## R-01 deep-dive: why a partial fix was deliberately not implemented

Investigated in full on 2026-07-10 (see `services/integration-hub/src/alarm/alarm.service.ts`, `alarm-ingestion.controller.ts`, `alarm-query.controller.ts`, and all 3 normalizers). Findings:

- Every alarm webhook endpoint (`/alarms/webhooks/{zabbix,alertmanager,grafana}`) authenticates via a single **global static token per source type** (`ZABBIX_WEBHOOK_TOKEN`, etc.) — there is currently no per-tenant credential or URL at the ingestion layer, and none of the 3 payload normalizers extract any tenant/customer/account-identifying field from the raw webhook body (confirmed via grep — no matches for tenant/customer/org/account across the normalizers).
- This means **there is no existing mechanism for an inbound webhook to identify which tenant it belongs to.** Blindly adding a `tenant_id` column and defaulting every new row to the single demo tenant would make the schema *look* fixed while leaving the actual multi-tenant ingestion problem completely unsolved — every alarm from every tenant would still land under one tenant_id, which is worse than clearly documenting the gap because it invites false confidence.
- The gap runs deeper than just `unified_alarms`: `alarm_ticket_map`'s uniqueness constraint is `ON CONFLICT (source_system, alarm_id)` with no tenant component — if two tenants both monitor infrastructure with the same `alarm_id` under the same `source_system` (plausible with generic/templated monitoring configs), one tenant's ticket mapping could silently overwrite another's. Any real fix must address this constraint too, not just add a column.
- **Recommended path forward** (not implemented): decide how tenant identity should enter the ingestion pipeline — options are (a) per-tenant webhook URLs/tokens (e.g. `/alarms/webhooks/zabbix/:tenantId` with a per-tenant secret), or (b) a tenant tag/label already present in the source system's alert payload that the normalizer extracts. Once decided: add `tenant_id uuid NOT NULL` to `unified_alarms` (backfilled to the single existing tenant for current rows, since 100% of today's data belongs to it), add it to `alarm_ticket_map`/`alarm_enrichment_jobs`, change the `alarm_ticket_map` unique constraint to `(tenant_id, source_system, alarm_id)`, index `unified_alarms(tenant_id, status)` and `unified_alarms(tenant_id, created_at)` for the list/SLA-refresh queries, and add `x-tenant-id`-based filtering to `alarm-query.controller.ts` matching the exact pattern already used in `connector.controller.ts`. This is a multi-file, multi-service change that deserves its own planning pass, not a bundled fix inside this investigation.
- If integration-hub is intended to be single-tenant-only (one shared NOC monitoring all customers, never exposed per-tenant), this entire risk should be **downgraded and documented as an accepted design constraint** instead of fixed — that's a product decision this investigation can't make unilaterally.
